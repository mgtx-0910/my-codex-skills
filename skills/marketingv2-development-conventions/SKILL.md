# MarketingV2 开发规约

在 marketingV2 项目中进行前端开发或代码审查时使用本 Skill。

## 优先复用现有能力

- 新增页面级组件、公共组件、工具方法、格式化方法、校验方法、请求辅助方法或公共样式前，先检索项目现有代码。
- 优先查看并复用 `src/components`、`src/utils`、`src/views`、`src/styles`、`src/store` 和 `src/apis` 中已有的实现。
- 现有组件或工具方法的行为符合需求，或通过向后兼容的小范围扩展即可满足需求时，应优先复用。
- 不要仅因为需要少量适配，就复制一套已有能力。
- 只有在项目中确实没有合适实现，或者复用会破坏原有职责、影响已有调用方时，才新增实现。
- 确需新增时，应放在项目既有目录中，并遵循实际模块的命名、接口和样式习惯。
- 用户明确要求独立实现时，以用户要求为准，但创建前仍需检查项目中是否存在相关能力。

## 现有目录结构与历史模块

- 项目默认前端目录规范用于指导新建模块，不代表所有历史模块都已经按该规范组织。
- 修改已有页面或历史模块前，先查看目标目录的实际层级、入口文件、组件位置、业务脚本和引用关系，以当前模块的真实结构为准。
- 对已有目录不要为了满足默认规范而强行移动、重命名、拆分或合并文件；除非用户明确要求重构，或当前改动确实必须调整目录才能完成。
- 对同时存在入口文件、业务脚本文件和 `components` 目录的历史模块，应保持其既有组织方式，按最小影响原则修改。
- 在历史模块内新增文件时，优先参考同目录及相邻模块已有的命名、导入和文件放置方式，不要机械套用另一套默认结构。
- 只有新建独立模块，或用户明确要求规范化重构时，才按项目默认目录规范组织文件，并评估路由、导入和已有调用方的影响。

## 目录层级与组件归属

- 目录结构应根据业务模块边界、文件职责和复用范围判断，不要仅根据 `import` 关系机械决定目录上下级。
- 同一业务模块、同一组件职责层级的页面组件或功能组件可以放在同一目录；一个组件引用另一个同级组件，不代表被引用组件必须放入引用方的子目录。
- 被多个兄弟组件复用的局部组件，通常应与这些组件保持同级，避免为单个引用关系增加无意义的目录层级。
- 只有在一组文件构成独立子功能、组件仅供单一父组件私有使用、同目录文件过多且存在清晰功能分组，或新建模块已经明确划分边界时，才考虑创建子目录。
- 修改历史模块时，以现有结构和实际职责为准，不要为了满足目录规则强行移动、重命名或拆分文件；确需调整时，应确认影响范围并保持导入关系可用。

## 页面架构与组件化

- 页面或路由组件以布局、模块组装和页面级流程协调为主，但可以持有本页面必要的局部状态；只有需要跨组件或跨页面共享的状态，才进一步抽离。
- 不要将接口请求、数据转换、表单校验、权限判断和复杂交互流程全部集中在一个页面或函数中。业务逻辑应根据职责封装到组件、Hook/Composable、Service、Store、领域模块或工具函数中。
- 按业务边界、交互边界和复用价值拆分组件，不要仅按代码行数机械拆分。组件应尽量保持单一职责，并拥有明确的输入、输出和副作用边界。
- 父子组件通过明确的 Props、Events、Slots 或项目现有的等价机制通信，避免直接操作对方内部状态、依赖内部实现或通过隐式副作用建立耦合。
- 避免过度拆分。只有当拆分能够降低复杂度、明确职责、提升复用性或方便测试时，才抽取新组件或新模块。
- 每份状态应尽量只有一个事实来源。根据已有状态或参数计算得到的数据，不要再次作为独立状态保存；同时区分接口数据、页面交互状态、URL 状态、表单状态和派生状态，避免将不同类型的状态无边界地集中到同一个全局 Store。
- 状态应放在能够满足共享需求的最近位置，不要为了统一管理而无理由地提升到全局。下层模块不应反向依赖页面组件，修改一个业务模块时应尽量控制影响范围。

### 复杂流程与状态建模

- 优先进行状态建模；当业务存在明确的有限状态、事件和状态转换关系时，优先使用状态机、Reducer 或集中式状态转换模型。
- 适合进行状态建模的场景包括：加载、成功、失败、空数据、重试等异步流程；创建、编辑、提交、审核、发布等多步骤流程；权限或业务阶段决定可执行操作；状态之间存在互斥关系、前置条件或异步副作用；多个布尔值相互组合导致状态难以理解和维护。
- 建模时应明确状态、事件、允许的转换、前置条件、副作用以及每个状态下可展示和执行的操作。
- 简单的开关、Tab、输入框和局部交互不需要强行使用状态机。状态机是建模方式，不代表每个场景都必须引入新的状态管理依赖。
- 复杂业务逻辑和状态转换应尽量能够脱离视图单独测试。目录和文件拆分应遵循项目现有约定，并以实际职责、复用范围和复杂度为依据，不要为了形式上的分层强制创建完整目录。

## 模块导出与导入

- 新建文件或非历史文件默认使用 ES Module 的 `export` / `import`。
- 历史文件已经使用 CommonJS 的 `module.exports`、`exports` 或 `require` 时，可以沿用原有导出导入方式，避免为了统一格式进行无必要的迁移。
- 不要仅因为新文件与 CommonJS 历史文件相邻，就让新文件采用 CommonJS；除非存在明确的兼容要求，新文件仍使用 ES Module。
- 修改历史文件时，不要求在同一次改动中迁移整个模块体系；如确需迁移，应先检查调用方并验证兼容性。

## 新建文件头部注释

- 新建页面、Vue 组件或业务脚本时，文件头部必须添加简短注释，说明该文件对应的功能和主要作用。
- Vue 文件使用模板注释，JavaScript 文件使用块注释；注释应放在文件头部，不要埋在实现中间。
- 注释内容至少说明“这是什么功能”和“主要负责什么”，应准确反映当前文件职责，避免只写文件名或无意义的套话。
- 不强制添加作者、日期等信息，除非项目现有模块或用户明确要求。
- 修改已有文件时，不需要为了补注释而扩大改动范围；只有新建文件必须遵守这条规则。

## 历史功能改动边界

- 修改已有或历史业务功能时，如果现有公共组件不满足当前需求，不要为了适配单个业务场景直接修改公共组件。
- 这类业务特例优先在当前页面或业务模块内新增局部组件、业务方法或适配逻辑，避免影响其他页面已有行为。
- 公共组件只有在功能本身不带业务属性、确实适用于多个场景时，才考虑提取或调整为公共能力。
- 公共方法按同样标准判断：业务规则、页面流程和特定接口字段相关的方法保留在业务模块内；稳定、无业务耦合、可跨页面复用的方法，才放入公共工具中。
- 调整公共组件或公共方法前，应评估已有调用方和兼容性，并补充受影响范围的测试。

## 业务字段取值与兜底规则

- 业务字段必须以接口文档、数据结构或用户明确说明为准，不要自行猜测字段别名或兼容不同接口格式。
- 除非文档或用户明确说明字段可能有多个来源，否则不要写多个业务字段的链式兜底，例如不要写 `prize_num || num || demo_num || 0`。
- 已确认字段有明确默认值时，只对指定字段做默认处理，例如 `prize_num || 0`；不要用其他未经确认的字段替代它。
- 字段缺失、类型不符合或数据结构与约定不一致时，没有明确默认规则就应显式报错、提示或保留异常状态，不要静默猜测和兜底。
- 其他业务条件、状态分支和异常处理也遵循同样原则：只有有明确依据的默认值或兼容分支才能实现，不能为了“尽量展示”而擅自增加兜底逻辑。

## 业务枚举与魔法数字

- 状态码、业务类型、操作类型、权限标识等有业务含义的固定值，必须使用项目全局共享的具名枚举。页面、模板和业务脚本不得在条件判断、`switch` 或配置映射中直接硬编码这类数字（包括数字字符串）。例如，用 `status === APPROVAL_STATUS.APPROVED` 替代 `status === 2`。
- 新增枚举前先查找并复用项目已有的公共枚举；没有对应定义时，按项目现有约定集中定义并导出，由各调用方统一引用，不要在页面或组件中重复定义，也不要仅因数值相同而混用不同业务含义的枚举。
- 枚举值和类型以接口或业务契约为准，不为了消除魔法数字改变实际取值或擅自进行类型转换。无业务含义的普通数字，如数组索引和计数初始值，不需要枚举化。
- 修改已有业务判断时，将本次涉及的魔法数字替换为共享枚举，不顺带重构无关代码。

## Action 与接口归属

- 业务页面中不要直接新增或硬编码相关 `action`，统一维护在 `src/apis` 目录下对应的 API 文件中。
- 新增或调整 `action` 前，先查找已有的 `api_xxx.js`，优先归入负责该业务的 API 文件，并沿用项目现有的导出和注册方式。
- API 文件归属可根据 Git 用户名提取用户缩写确定。例如 Git 用户名为 `caihongmin` 时，用户缩写为 `chm`，相关 `action` 应维护在 `src/apis/api_chm.js`。
- `src/apis/api_xxx.js` 中导出的键名必须在所有 API 文件范围内保持唯一，不仅要避免同一个文件内部重复，也要避免不同 API 文件之间重复；因为 `main.js` 合并对象时，重复键可能被后加载的文件静默覆盖。
- 新增 API 键名前应先检索 `src/apis/api_*.js`，确认不存在同名键；如果是同一个接口能力，应复用或调整已有键，不要再次声明。
- 业务页面只通过已注册的 API 对象引用 `action`，不要在页面中重复声明同一个接口标识。
- 一般情况下，业务页面使用负责人的独立 API 对象引用，例如 `this.$api_chm.xxx`，不要使用 `main.js` 合并后的 `this.$api.xxx`；只有确有跨负责人或公共 API 使用需求时，才使用合并对象。
- 如果一个 `action` 的归属不明确，应先确认负责人或现有模块归属，不要随意新建页面内常量或放入不相关的 API 文件。

## 完成后的验证顺序

代码实现完成后，必须按以下顺序验证，前一步发现问题时先修复，再继续下一步：

1. **检查 ESLint**
   - 优先执行 `npm run lint`。
   - 只检查局部代码时，也可以使用项目现有的 ESLint 方式对相关文件进行检查。
2. **进行安全审计**
   - 检查本次改动是否引入 XSS、注入、危险 URL 或路径处理、敏感信息日志、权限绕过等安全问题。
   - 优先执行项目已有的安全测试或安全审计脚本，例如 `node src/utils/__tests__/security-runner.js`。
3. **执行单元测试**
   - 为新增或修改的行为补充聚焦测试。
   - 执行与本次改动直接相关的测试文件或项目测试命令，确认功能行为和回归风险。

最终汇报时，应分别说明 ESLint、安全审计和单元测试的执行结果；没有实际执行的检查不得表述为已通过。
