## 执行

1. 按用户指定选择环境；无法判断环境时询问。用户明确要求从某个分支直接打包时，以该分支为打包分支，不自动合并到默认分支；用户给出分支但未明确要求直接从该分支打包时，将该分支作为源分支合并到所选环境的默认打包分支，处理冲突并核实结果，再从合并结果打包。用户未提供分支时，不额外合并，使用最新远端默认打包分支。用户另有明确的合并目标或流程时遵从用户要求。依用户要求处理推送，不假称已推送。构建前记录实际打包分支及提交 SHA，保护其他工作区的改动，必要时使用独立工作区。

2. 在目标提交的 `code_V2.0/web` 核对 `package.json`、环境配置、Node 版本、依赖与实际输出目录。优先使用项目已有的 `node_modules`，不要每次发布都重新安装依赖；独立工作区可复用对应 Web 项目的现有依赖，并核实构建实际输入和输出路径不会影响其他工作区。只有构建出现依赖缺失、不兼容等错误，或确认现有依赖无法使用时，才按需安装或修复依赖。昌吉配置中的业务接口可能指向线上域名，按目标分支原配置检查并报告，不自行改动。运行对应构建命令；校验日志及产物完整性，不能仅依赖退出码（项目曾出现未处理 Promise 错误但退出码为零）。旧项目的构建可能运行数分钟甚至更久，进程仍在运行且资源占用正常时继续等待，不要因暂时没有日志直接终止。

   `code_V2.0/web/package-lock.json` 可能被 `.gitignore` 忽略而在分支中缺失。此时先核对当前分支的 `package.json` 与对应项目工作区的 `package.json` 一致，再复制对应的 `package-lock.json` 到本地构建目录；不要把该锁文件强行加入提交，也不要用其他项目的锁文件替代。缺少锁文件且无法确认依赖对应关系时，停止发布。

3. 昌吉 `npm run build:xj` 的产物通常位于 `code_V2.0/web/distDlbs/xinjiang-YYYYMMDD-HHMM`（同一分钟重复构建可能带 `-2`、`-3` 后缀）这样的最新时间戳子目录。上传该最新子目录的内容到远端 `/web/`，不要把 `distDlbs` 或时间戳目录本身再套一层；通常包括 `static`、`favicon.ico`、`index.html` 和 `route-loaders.manifest.json`。构建生成的旧时间戳目录不属于本次发布，不要上传。

4. 核实服务器登录后的实际目录和网站入口。先列出远端 `/web/`，记录本次构建会覆盖的文件清单；不生成本地或远端备份文件，不创建备份目录。不要清空目录、删除远端旧文件或删除不属于本次发布的文件。优先上传 `static` 等资源和其他引用文件，最后上传 `index.html`；中途失败则停止并报告已上传范围和失败位置。可跳过已确认内容相同的文件，但必须能说明跳过依据。

5. 构建期间远端分支出现新提交时，不影响本次已经开始的构建和发布，不自动重新获取、切换分支或重新打包，也不把分支变化作为发布阻塞条件。继续发布本次实际构建的 SHA；只有用户主动明确要求重新打包时，才重新获取最新分支、重新构建并发布。

6. 校验上传内容，并通过环境访问地址验证入口及引用的资源。至少下载或请求远端 FTP 入口和 HTTP 入口，比较本地产物、FTP 入口和 HTTP 入口的 SHA256；抽查入口引用的 CSS、JS、`route-loaders.manifest.json` 等资源并确认 HTTP 状态为 200。若不能验证关键业务页面，明确说明。报告环境、实际打包分支、实际发布 SHA、构建与发布结果、未生成备份文件、验证范围和实际限制。不要凭文件夹修改时间判断子目录内容是否更新。

H5 不在默认范围。发布前后保留既有未提交文件；除用户明确要求保存的本技能文件外，不要将密码写入项目文档。用户明确要求发布即授权本次环境发布；技能本身不额外要求确认。
